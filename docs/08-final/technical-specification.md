## 2. Назначение и цели системы

### 2.1. Назначение

Calculator — веб-приложение, автоматизирующее расчёт стоимости продуктов и услуг для малого бизнеса. Система избавляет от ручного пересчёта цен в Excel: пользователь один раз настраивает справочник материалов и формулы, а система гарантирует актуальность итоговой стоимости при каждом открытии расчёта.

### 2.2. Цели

- Предоставить гибкий инструмент настройки ценообразования без участия разработчика
- Обеспечить актуальность цен: при изменении стоимости материала все расчёты автоматически отражают новую цену
- Разграничить доступ к функциям системы через ролевую модель прав

---

## 3. Требования к функциональным характеристикам

### 3.1. Перечень подсистем

| Подсистема | Описание |
|---|---|
| Управление материалами | Справочник материалов и их групп |
| Управление формулами | Конструктор математических выражений с плейсхолдерами |
| Управление расчётами | Создание, сохранение и пересчёт расчётов на основе формул |
| Управление пользователями | Создание учётных записей и назначение ролей |
| Управление ролями | Создание ролей с гибким набором прав доступа |
| Аутентификация | Вход по логину и паролю, выдача JWT-токена |

### 3.2. Функциональные требования

#### 3.2.1. Управление материалами

- Система хранит справочник материалов с полями: название (уникальное), цена за единицу (≥ 0), единица измерения (необязательно), группа
- Пользователь с соответствующими правами может создавать, редактировать и удалять материалы
- Материалы организованы в группы. При удалении группы пользователю предлагается выбор: удалить вместе с материалами, перенести в другую группу
- Удаление материала, используемого в расчёте, не удаляет расчёт, но делает его невычислимым

#### 3.2.2. Управление формулами

- Формула содержит: название (уникальное), математическое выражение, группу
- Выражение поддерживает плейсхолдеры двух типов:
  - `{название_группы}` — пользователь выберет материал из указанной группы
  - `{const}` — зарезервированное ключевое слово, пользователь введёт произвольное число
- Пример выражения: `({wood} + {glue}) * {const}`
- Удаление формулы каскадно удаляет все расчёты, основанные на ней

#### 3.2.3. Управление расчётами

- Расчёт создаётся на основе формулы: для каждого плейсхолдера `{группа}` выбирается материал из группы и вводится количество; для `{const}` вводится число
- Результат расчёта вычисляется при каждом открытии по актуальным ценам материалов
- Если материал в позиции расчёта удалён — результат не отображается, позиция подсвечивается как незаполненная

#### 3.2.4. Управление пользователями и ролями

- Суперадмин создаётся при инициализации системы и не может быть удалён (защита в UI и триггером на уровне БД)
- Пользователь без роли может войти в систему, но не имеет доступа ни к каким функциям
- Роль — именованный набор прав. Один пользователь имеет не более одной роли

**Список прав доступа:**

| Область | Права |
|---|---|
| Материалы | Просмотр, Создание, Редактирование, Удаление |
| Формулы | Просмотр, Создание, Редактирование, Удаление |
| Расчёты | Просмотр, Создание, Редактирование, Удаление |
| Роли | Создание, Редактирование, Удаление |
| Пользователи | Создание, Удаление |

### 3.3. Границы системы

**Входит в scope:**
- Справочник материалов и формул
- Создание и пересчёт расчётов
- Ролевая модель прав доступа
- Веб-интерфейс и десктоп-интерфейс

**Не входит в scope:**
- Складской учёт количества материалов
- Интеграции с внешними системами (1С, CRM и т.д.)
- Многоарендная архитектура — каждый клиент разворачивает свой экземпляр
- Экспорт расчётов в PDF / Excel

## 4. Требования к архитектуре

### 4.1. Архитектурный стиль

Система построена по паттерну **PCMEF** (Presentation – Control – Mediator – Entity – Foundation). Зависимости направлены строго сверху вниз: P → C → M → E → F. Слои взаимодействуют через явные интерфейсы-контракты.

| Слой | Ответственность | Реализация |
|---|---|---|
| Presentation (P) | UI, отображение, ввод | React (веб), JavaFX (десктоп) |
| Control (C) | REST-контроллеры, валидация, JWT | Spring MVC Controllers |
| Mediator (M) | Бизнес-логика, транзакции, права | `*ServiceImpl` + `*ServiceProxy` + `*ServiceDecorator` |
| Entity (E) | JPA-сущности, бизнес-объекты | Lombok + Jakarta Persistence |
| Foundation (F) | Доступ к данным, репозитории | Spring Data JPA |

### 4.2. Применяемые паттерны GoF

| Паттерн | Классы | Назначение |
|---|---|---|
| Proxy | `*ServiceProxy` | Централизованная проверка прав доступа |
| Decorator | `*ServiceDecorator` | Логирование и аудит действий без изменения основного кода |
| Builder | `Calculation.Builder` | Пошаговое построение объекта расчёта |
| Strategy | `DeleteGroupStrategy` | Инкапсуляция стратегии удаления группы |

### 4.3. Интерфейсы между слоями

- Control → Mediator: `IMaterialService`, `IFormulaService`, `ICalculationService`, `IUserService`, `IUserRoleService`, `IMaterialGroupService`, `IFormulaGroupService`
- Mediator → Foundation: Spring Data `JpaRepository<Entity, Integer>`

## 5. Требования к REST API

- Версионирование: `/api/v1/...`
- Формат данных: JSON
- Аутентификация: Bearer JWT в заголовке `Authorization`
- Стандартные HTTP-статусы: 200, 201, 204, 400, 401, 403, 404, 500

**Основные группы эндпоинтов:**

| Группа | Базовый путь |
|---|---|
| Аутентификация | `POST /api/v1/auth/login`, `POST /api/v1/auth/logout` |
| Материалы | `/api/v1/materials`, `/api/v1/material-groups` |
| Формулы | `/api/v1/formulas`, `/api/v1/formula-groups` |
| Расчёты | `/api/v1/calculations` |
| Пользователи | `/api/v1/users` |
| Роли | `/api/v1/roles` |

---

## 6. Требования к безопасности

- Аутентификация по логину и паролю; пароли хранятся в виде BCrypt-хеша (cost 10)
- Авторизация на основе 17 атомарных прав доступа, объединяемых в роли
- JWT-токены для stateless-аутентификации
- Суперадмин (`is_super_admin = true`) защищён от удаления и снятия флага триггерами на уровне БД
- Слой Mediator/Proxy проверяет права до выполнения любой операции

---

## 7. Требования к базе данных

- СУБД: PostgreSQL 16
- Нормализация: третья нормальная форма
- Индексы: на внешние ключи и часто фильтруемые поля
- Ограничения целостности: NOT NULL, UNIQUE, CHECK (`price >= 0`, `quantity >= 0`)
- Каскадные удаления: формула → расчёты → позиции расчётов
- Триггеры: защита суперадмина от удаления и сброса флага

---

## 8. Требования к развёртыванию

- Контейнеризация: Docker + docker-compose
- Стек: PostgreSQL 16 + Spring Boot JAR + React (Nginx)
- Конфигурация через переменные окружения: `SPRING_DATASOURCE_URL`, `SECURITY_JWT_SECRET`
- Десктоп-клиент: самодостаточный исполняемый файл (встроенный JRE, не требует установки Java)
