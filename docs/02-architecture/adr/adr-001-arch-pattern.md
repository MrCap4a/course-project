# ADR-001: Выбор архитектурного паттерна

**Статус:** Принято  
**Дата:** 2026-03-01  
**Автор:** [ФИО]

---

## Контекст

Необходимо выбрать архитектурный паттерн для системы конфигурируемого калькулятора ценообразования. Система должна поддерживать два типа клиентов (Desktop на JavaFX и Web-интерфейс в браузере), централизованную бизнес-логику и доступ к реляционной БД. Требование курсового проекта — использование паттерна PCMEF (Presentation-Control-Mediator-Entity-Foundation).

---

## Рассмотренные варианты

### Вариант 1: Классический PCMEF (монолитный Desktop)
Все слои (P, C, M, E, F) находятся в одном JVM-процессе. Взаимодействие между слоями — прямые вызовы методов.

**Плюсы:**
- Простота реализации
- Нет сетевого взаимодействия
- Меньше кода

**Минусы:**
- Невозможно подключить Web-клиент
- Оценка — не выше 4 (траектория А)
- Нет разделения ответственности между клиентом и сервером

### Вариант 2: Enterprise PCMEF (Desktop + Web + Server) ✅ Выбран
Presentation-слой разделён физически: Desktop-клиент содержит Presentation + Control локально; Web-клиент содержит только Presentation в браузере. Control (REST API), Mediator, Entity, Foundation централизованы на сервере Spring Boot. Единая точка интеграции — REST API поверх HTTPS/JSON.

**Плюсы:**
- Поддержка двух типов клиентов из одного сервера
- Чёткое разделение ответственности
- Возможность независимого масштабирования клиентов
- Соответствует траектории Г (Enterprise) — экзамен-автомат при успешной защите

**Минусы:**
- Выше сложность реализации (~160 часов)
- Требует настройки REST API и аутентификации JWT

### Вариант 3: Микросервисная архитектура
Разбить систему на несколько независимых сервисов.

**Плюсы:**
- Максимальная масштабируемость

**Минусы:**
- Избыточная сложность для учебного проекта одного разработчика
- Нет явного требования в методических указаниях

---

## Решение

Выбран **Вариант 2: Enterprise PCMEF**.

Распределение слоёв:

| Слой | Расположение | Технология |
|---|---|---|
| Presentation (Desktop) | Desktop-клиент | JavaFX |
| Control (Desktop) | Desktop-клиент | JavaFX Controllers |
| Presentation (Web) | Браузер | HTML/CSS/JavaScript |
| Control (Server) | Сервер | Spring Boot @RestController |
| Mediator | Сервер | Spring Boot @Service |
| Entity | Сервер | JPA @Entity |
| Foundation | Сервер | Spring Data @Repository |

Дополнительный слой **DTO** введён на сервере для отделения внутренних JPA-сущностей от JSON-контрактов API.

Все зависимости направлены строго вниз: `P → C → M → E → F`. Циклические зависимости отсутствуют. Слои общаются через явные интерфейсы: `IMaterialService`, `IUserService`, `IMaterialRepository`, `IUserRepository`.

---

## Последствия

- Необходимо реализовать REST API (15+ эндпоинтов) с документацией OpenAPI
- Desktop-клиент взаимодействует с сервером через HTTP-клиент (Spring RestTemplate / OkHttp)
- Web-клиент взаимодействует через браузерные HTTP-запросы
- Требуется настройка CORS на сервере для Web-клиента
