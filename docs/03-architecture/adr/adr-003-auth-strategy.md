# ADR-003: Стратегия аутентификации

**Статус:** Принято  
**Дата:** 2026-03-01  
**Автор:** [ФИО]

---

## Контекст

Система поддерживает два типа клиентов: Desktop (JavaFX) и Web (браузер). Оба клиента обращаются к одному REST API. Необходим механизм аутентификации, который работает без сессий на сервере (stateless), совместим с обоими клиентами и поддерживает ролевую авторизацию (роли и разрешения).

---

## Рассмотренные варианты

### HTTP Sessions (Cookie-based)
**Плюсы:** Простота реализации, встроенная поддержка в Spring Security.  
**Минусы:** Stateful — сервер хранит состояние сессии. Не подходит для Desktop-клиента без браузера. Плохо масштабируется (нужен общий session store при горизонтальном масштабировании).

### Basic Auth (логин/пароль в каждом запросе)
**Плюсы:** Очень простая реализация.  
**Минусы:** Пароль передаётся в каждом запросе — высокий риск перехвата. Нет возможности выдать короткоживущий токен.

### JWT (Access + Refresh токены) ✅ Выбрано
**Плюсы:**
- Stateless — сервер не хранит сессии
- Работает одинаково для Desktop и Web клиентов
- Короткоживущий access-токен снижает риски при компрометации
- Refresh-токен позволяет обновлять access без повторного ввода пароля
- Встроенные claims для ролей и разрешений

**Минусы:**
- Сложнее реализовать инвалидацию токенов до истечения срока
- Требует безопасного хранения токенов на клиенте

### OAuth2 / OpenID Connect
**Плюсы:** Стандартизировано, поддержка внешних провайдеров.  
**Минусы:** Избыточная сложность для учебного проекта без внешних провайдеров идентификации.

---

## Решение

**Механизм:** JWT (JSON Web Token) с парой access + refresh токенов.

### Параметры токенов

| Параметр | Access-токен | Refresh-токен |
|---|---|---|
| Срок жизни | 15 минут | 7 дней |
| Хранение (Web) | Memory / httpOnly cookie | httpOnly cookie |
| Хранение (Desktop) | В памяти приложения | Защищённое хранилище |
| Алгоритм подписи | HS256 | HS256 |

### Эндпоинты аутентификации

| Метод | Эндпоинт | Описание |
|---|---|---|
| POST | `/api/v1/auth/login` | Логин → возвращает access + refresh токены |
| POST | `/api/v1/auth/refresh` | Обновление access-токена по refresh-токену |
| POST | `/api/v1/auth/logout` | Инвалидация refresh-токена |

### Авторизация

Роли и разрешения хранятся в БД (таблицы `roles`, `permissions`). Claims в JWT содержат список разрешений пользователя. Spring Security проверяет разрешения через `@PreAuthorize` на уровне контроллеров.

### Хеширование паролей

Пароли хранятся в БД в виде хеша BCrypt (strength = 12). Открытый пароль нигде не сохраняется и не логируется.

---

## Последствия

- Секрет подписи JWT задаётся через переменную окружения `JWT_SECRET`
- При компрометации refresh-токена администратор может инвалидировать его через удаление из таблицы `refresh_tokens`
- Desktop-клиент должен обновлять access-токен автоматически при получении HTTP 401
- HTTPS обязателен в продакшне для защиты токенов при передаче
