# ADR-002: Выбор базы данных и ORM

**Статус:** Принято  
**Дата:** 2026-03-01  
**Автор:** [ФИО]

---

## Контекст

Система хранит взаимосвязанные сущности: материалы, группы материалов, формулы, группы формул, расчёты, пользователи, роли. Необходима реляционная БД с поддержкой транзакций, внешних ключей и сложных запросов с фильтрацией. Требуется ORM для маппинга JPA-сущностей и работы с Spring Boot.

---

## Рассмотренные варианты

### СУБД

#### SQLite
**Плюсы:** Нет отдельного сервера, простота настройки.  
**Минусы:** Ограниченная поддержка конкурентного доступа, не подходит для многопользовательской работы, слабая поддержка в Spring Boot для продакшн-сценариев.

#### MySQL
**Плюсы:** Широко распространена, хорошая документация.  
**Минусы:** Лицензионные ограничения (Oracle), уступает PostgreSQL по функциональности (нет нативного JSON, меньше типов данных).

#### PostgreSQL ✅ Выбрана
**Плюсы:** Открытая лицензия, богатые типы данных, полная поддержка ACID, хорошая интеграция со Spring Boot, рекомендована методическими указаниями.  
**Минусы:** Требует отдельного сервера.

---

### ORM

#### JDBC (чистый)
**Плюсы:** Полный контроль над SQL.  
**Минусы:** Много шаблонного кода, нет автоматического маппинга объектов.

#### MyBatis
**Плюсы:** Гибкость SQL.  
**Минусы:** Требует ручного написания всех запросов, плохо интегрируется со Spring Data.

#### Spring Data JPA / Hibernate ✅ Выбрано
**Плюсы:** Минимальный шаблонный код, автоматические CRUD-методы через `JpaRepository`, интеграция с `@Transactional`, стандарт для Spring Boot.  
**Минусы:** Возможна N+1 проблема при неаккуратной работе с ленивой загрузкой (митигируется через `@EntityGraph`).

---

## Решение

**СУБД:** PostgreSQL 15+  
**ORM:** Spring Data JPA (Hibernate в качестве провайдера)

Конфигурация подключения задаётся через `application.yaml`:
```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/calculator
    username: ${DB_USER}
    password: ${DB_PASSWORD}
  jpa:
    hibernate:
      ddl-auto: validate
    show-sql: false
```

Стратегия миграций схемы: DDL-скрипты версионируются вручную в `docs/04-database/ddl.sql`. `ddl-auto: validate` обеспечивает проверку соответствия сущностей схеме без автоматического изменения таблиц в продакшне.

Транзакции управляются через аннотацию `@Transactional` на уровне слоя Mediator (`@Service`). Уровень изоляции по умолчанию: `READ_COMMITTED`.

---

## Последствия

- Необходима установка PostgreSQL перед запуском приложения
- Переменные окружения `DB_USER` и `DB_PASSWORD` должны быть заданы
- DDL-скрипты (`ddl.sql`, `triggers.sql`, `seed.sql`) выполняются вручную при первом развёртывании
- Для тестов используется H2 in-memory БД (`scope: test`) — не требует установки PostgreSQL в CI
